# Spec C4: reconstructing the fairness records of past months (solver v3)

## Status

`DRAFT` · **Risk tier: CRITICAL** — it writes production data: `fairnessMonth` documents in the
production dataset that every later v3 solve, the «Equidad» panel and the DL floor read as the truth
about who was eligible in a past month. A wrong record silently creates or erases debt for real
people for three months. The parent's §11 table assigns this tier («production data»); CLAUDE.md
puts any production Sanity write behind a dry run and Frank's explicit consent.

## Outcome

- **Primary outcome.** Each lookback month that will feed a v3 solve and was planned before any v3
  writer existed gets a `fairnessMonth` record with `source: "reconstructed"`, written **through
  C2's one write executor** (IF2-22; parent A4), after Frank has read a per-person table of exactly what will
  be written and what balances it implies, and consented to that table. The months are August and
  September 2026 first — the exit of «→ C4» (A37); October 2026 on or after 2026-11-01 (it must be
  past — A21); then every month confirmed under v2 before cutover, **each as it becomes past** (A21;
  until then it reads «sin registro»). A v2-planned month that a v3 Auto confirm includes in its
  horizon gets a `source: "auto"` record at that confirm (A27: the confirm creates a record for
  every recordless horizon month, stored services or not); that record is not the reconstruction's,
  so the month leaves C4's scope and its row reads «no lo escribió la reconstrucción: no se toca» —
  the expected outcome, not a failure (R14).
- **Operator.** Frank reviews and consents; Claude (or Frank) runs the script from a checkout whose
  `.env.local` points at production.
- **Problem today.** Nobody recorded who was eligible in a past month. The pool ticks live in one
  overwritten singleton; its revision history starts 2026-09-29. Under parent F3 a lookback month
  with no record counts for nothing — so without this child, the first v3 runs would balance against
  an empty past, which is the very gap the program exists to close.
- **Success measure.** For each reconstructed month: Frank has signed off the table; the record that
  landed has the content hash the reviewed dry run printed; a second dry run reports «sin cambios»
  for every month and plans zero writes; the «Equidad» panel preview (C2) shows those months as
  «reconstruido» and Frank reads the resulting balances as correct.

## Interfaces

C4 owns no data shape. It **consumes** C1's field, C2's record, write-request module, resolver,
ledger, builders and formatter, and C3's cadence setting and name resolver, and **provides**
reconstructed records and an operator CLI. **Every C2 shape is C2's, by `IF2-` ID** (C2 §7; C2 §7.4
row «C4» is the list of C4's obligations as C2 states them): this section names the items and says
what C4 does with each, never what they look like. C1 and C3 shapes are cited by section. Where a
sibling renames a thing, its name wins and its ID or section survives.

### Consumes from C1

- The stored field `countsForFairness` and its read rule (C1 §9 «C1 provides», rows «Stored field»
  and «Read-rule module»; parent L1), applied by C2's builders (IF2-24, IF2-26) and ledger (IF2-10,
  IF2-11). C4 writes no query of its own for it. Used for: which seats count toward a join month
  (R5), the per-service «cuenta» column of the table (R11 — C1 lists C4 as a consumer that prints
  it), and the balance preview (R11).
- C1 §9 «Facts the consumers must hold», as C4 holds them: the past-month rule is **client-side**
  (C1 §6.0, C1-D7) — a hand-built admin request can still set a past service's flag, and a date
  move, which C1 does not gate, can carry a service and its flag into or out of a past month. C4
  therefore never treats a past month's counted set as frozen: it reads every flag live, binds the
  effective flags it read into the plan (R15's service-input digest), and its runbook tells the
  operator to re-run the dry run after any such change (R21).

### Consumes from C2

1. **The record** — IF2-2 (the stored document), IF2-3 (`LogicalRecord`), IF2-1 (role keys,
   statuses, lines, units), and IF2-4's `FairnessMonthWrite` as the body type only (the resolver
   returns it without `source` and `expectedRev`; C4's transform keeps that shape; C4 never calls the
   PUT). C4 never constructs an id, `_key`, `name`, stamp or `contentHash` (R2;
   IF2-2's «only the write-request module constructs one»); it reads records only through IF2-25 and
   IF2-20. Its records carry the reconstruction actor's stamps (C2 WR-14; R10).
2. **The write-request module** — IF2-18 (`Actor`, `validateFairnessMonthWrite`), IF2-19
   (`contentHashOfWrite`, `contentHashOfStored`; «intact» is IF2-19's equality), IF2-20 (the
   stored-record parser), IF2-21 (the write decision), IF2-22 (the write executor), with IF2-6's
   refusal codes. The script imports this module, never `app/utils/fairnessMonthCommit.ts` (C2 WR-1).
   C4's own use:
   - **Validation (IF2-18).** C4 passes every transformed body (order below) through IF2-18 as actor
     `reconstruction`, with IF2-18's `currentMonth` argument set to the current CDMX month
     (`YYYY-MM` of R1's `today`) — the same value the run hands IF2-21 and IF2-22's
     `stamps.currentMonth` — before planning it; an invalid body refuses the run (exit 2), no plan
     written. WR-4's «at most the current month + 12» ceiling can never refuse a body of R1's
     strictly past months, so the argument never changes a C4 verdict; it is passed because IF2-18
     takes it.
   - **Parsing (IF2-20).** Every **stored** record the script hands the ledger, compares against or
     backs up passes through IF2-20 first; a refusal is a malformed read (R3: exit 1, nothing
     written). The rollback alone does not use it (R18 reads `_id`, `_rev`, `source` and
     IF2-19's recomputed hash only, so a malformed record can still be listed and refused there).
   - **Planning (IF2-21).** The dry run plans each month by calling IF2-21 with actor
     `reconstruction` — the function the executor itself runs — so a planned action and the
     executor's verdict cannot differ («Decision per month», R14).
   - **Writing (IF2-22).** Every create, replace and delete goes through IF2-22 with actor
     `reconstruction`, called only from the CLI file (R20, IF2-23). The script builds the read client
     IF2-22's read-client contract requires (R19) and hands the executor only the plan's actions (R15,
     R16). For a month decided create or replace the executor reads the listed members itself and
     takes each item's `name` from that read; a listed id with no member document refuses that month
     `member_unknown` (C2 WR-14 row 9) — the run then stops (R16). The mutation forms (WR-11's
     revision-asserted patch for a replace, WR-14's patch-plus-delete transaction for a delete, never
     `createOrReplace`) are IF2-22's, not C4's.
3. **The resolver** — IF2-15 (`resolveMonthEligibility`; it is **not** in the write-request module,
   C2 §7.2). C4 hands it, per month, `members` = IF2-27's rows **unaltered** and a `config` whose
   three pools are R4's hypothetical ticks and whose restrictions and cadence settings are today's,
   from IF2-28 parsed by `solverConfigFromDocument`, **unaltered** — the overrides file never edits
   the `config` (D11). C4 never branches on a refusal reason or issue code: every `ok: false` of
   IF2-15 is terminal for the run. C4 relies on RES-8's invariant (an `ok: true` body passes IF2-18).
   **Order (C4's own):** (i) the resolver runs per month on that `config`; any `ok: false` refuses
   the run (exit 2) before any body is transformed, reported per R13, never by name or identifier on stdout; there
   is no body to correct, so no override can clear it and the fix is in `solverConfig` (the same
   rules refuse v3's Auto: C2 §7.4 row «C6»; C3 §6.12). (ii) Only on `ok: true` do R5–R8
   **transform** the returned body: R5's join bounds only narrow it; R6–R8 set what the overrides
   file says (a status, an exact rule, `exempt`, the cadence setting, join months, blocked dates),
   which may also widen a cell, or add a `people` item for a worship member the resolver did not
   list (R8 «adding a person»; C2 WR-17 names this transform). (iii) The transformed body goes
   through IF2-18, which catches any contradiction an override introduced (A11's pair and A38's
   overlap included). By RES-8, a refusal at (iii) can only come from C4's own transform — an
   overrides-file contradiction, or a C4 bug that R5–R8's tests must prevent — never from today's
   rules.
4. **The ledger** — IF2-10 (`computeFairnessLedger`, `LedgerInput`, `LedgerService`) and IF2-11
   (`keepVoiceSeats`, the record-free seat step), over IF2-8's output shapes and IF2-9's notes.
   C4 counts no seat itself: R5's join months read only IF2-11's kept seats (so a dropped duplicate
   or a second seat never sets one, and the join month and the ledger read the same seats); R7's
   «tuvo» counts and R11's seats come from the ledger's integers (IF2-8 `held`, `Figures.seats`;
   A39); the preview's figures are IF2-10's output. C4 builds `LedgerInput` from IF2-26's rows
   (mapped to `LedgerService`), IF2-27's rows as `members`, and the records R11 names.
5. **The read builders** — IF2-24 (freezing-services counts, R1's skip), IF2-25 (records; C4 passes
   its own bound and keeps the months it needs), IF2-26 (voice role documents of all three types in
   the join and preview windows), IF2-27 (the worship roster: IF2-15's `members`, C3's roster for
   R13's name lookups, R4's Tipo source, R9's availability source, R8's roster check) and IF2-28
   (the rule set; `null` refuses the run, R3). The script writes no roster, rule, record or role
   GROQ of its own, and runs every builder only on its token-carrying, `published`-perspective,
   no-CDN read client (R3, R19).
6. **The display formatter** — IF2-13. The table and preview format every fairness figure through
   it, from the ledger's tenths, never from hundredths, and never format or round a number
   themselves (A17); seat counts are the ledger's integers (A39).

    shows (default: the month after the last requested month);
  - no write flag → dry run; `--apply --plan <file>` → writes exactly the reviewed plan; `--plan`
    is refused inside the repository like `--out` (R11);
  - `--rollback` → plans deletions (dry run; `--overrides` and `--preview-run` refused with it,
    R18); `--rollback --apply --plan <file>` → deletes exactly the reviewed plan;
  - exit codes: `0` done (dry run printed, or every planned write landed); `2` refused before any
    write; `1` failed or partial.

It never carries a display name, alias, `_key`, `id`, `ruleKey`, a hash prefix of one, or a member `_id` (R12). **Refusal report:** every refusal that happens **after** the reads (resolver, validator, overrides file, the plan binding of R15) also writes a private Markdown report to `--out` — already validated before any read (R11). Under the same refusal ordinal, the report names each refused rule by its config ordinal and its raw `_key`, and each member by display name and `_id`, with the reason and the fix — the private file is the only place the ordinal printed on stdout meets the key. This is where Frank finds what to edit, and where he copies an `_id` for the overrides file (D8). A refusal **before** any read (a path inside the repository, a missing token, a month not past, a flag combination) writes nothing | Inference is lossy (evidence); Frank decides each case through the overrides file; A7/L4 refuse an unresolvable name | Each anomaly type has a fixture case and appears in the table, including «fecha bloqueada perdida» for a fixture reconstructed record holding a date the member has since deleted; each refusal exits 2 with no table or plan written, and each post-read refusal writes the refusal report (with the fixture names) while stdout stays name-free |

### Decision per month

Planned in the dry run by calling C2's write decision (IF2-21) with actor `reconstruction` — the same
function the executor (IF2-22) re-runs at write time, so its rows and order are C2 WR-14's and IF2-6
names every verdict; C4 adds only the skip of R1 and the labels. The table below is C4's mapping of
those verdicts to planned actions and labels, not a second decision.

| Existing record for the month (as read) | Planned action | Executor verdict | Table / stdout label |
|---|---|---|---|
| any, month not past | — (the run refused, R1) | `not_past_month` | — |
| none, month has no stored weekend services and no counted specials | skip (C4's own rule, R1) | — | «sin servicios guardados» |
| any `source`, intact, `contentHash` equal to the planned one | **no-op** (nothing sent) | `unchanged` | «sin cambios» |
| none | **create** with `expectedRev: null` | `created` (an `_id` collision at write time → `record_exists`, that month refused) | «crear» |
| `source` ≠ `"reconstructed"` (hash differs) — e.g. a v3 Auto confirm's record (A27) or a «Registrar» record | refuse | `not_reconstruction_owned` | «no lo escribió la reconstrucción: no se toca» |
| `"reconstructed"`, **not** intact | refuse | `record_edited` | «editado después de reconstruir: no se toca» |
| `"reconstructed"`, intact, planned hash differs | **replace** with `expectedRev` = the `_rev` read in the dry run; the table shows the per-person diff | `replaced` (a changed `_rev` → `stale_revision`) | «reemplazar» |
| a month planned **create** or **replace** whose body lists a `memberId` that has no member document when the executor reads it (C2 WR-14 row 9; IF2-22) | the planned create or replace (nothing extra is planned) | `member_unknown` — that month refused, the run stops (R16) | «crear» / «reemplazar» in the plan; the refusal in the apply report |

Every person a planned body lists is on the roster the dry run read, and `--apply` re-derives from
the live roster (R15), so a member deleted before the apply changes the fingerprint and refuses the
run before any write; `member_unknown` is reachable only for a deletion between that re-derivation
and the executor's own member read — a race the executor closes, not one C4 can plan around.

## Behavior and invariants

- **Required behaviour:** R1–R23.
- **Preserved:** CDMX dates (service month = stored date string); `saturdarSongs` untouched; the five
  member seats are read through C2's builders; canonical documents only; `_key` on every array item
  (minted by C2's module); no `revalidate*` call is needed (no ISR page reads `fairnessMonth`, C2
  WR-13, and the script changes no content a page renders); v2 behaviour unchanged (records are
  inert under v2, parent §13).
- **Data:** the only documents this script can create, replace or delete are `fairnessMonth`
  records it wrote, of past months, through C2's executor (A4). It reads members' availability,
  which is why its outputs are private.
- **Security/privacy:** no member name, and no document identifier that may embed one (R12), in
  the repository or on stdout; no member name in Sanity beyond the
  display-name text C2's record stores; the record's dotted id keeps it out of unauthenticated reads
  (A2); private files only under a path outside every working tree.
- **Interaction with the policy:** the DL join months this script records are the start of each
  pre-cutover member's DL line, so they decide where the DL floor's look-back begins (F10); the
  cadence setting it records makes the cadence members' Sundays set-asides in those months (F5, F7);
  a month it skips, or that is not yet past, stays «sin registro, no cuenta» (F3, A21).
- **Failure and recovery:** a failed read → nothing written, exit 1; a refused input or a missing
  token → nothing read or written, exit 2; a partial apply → stop, report, re-run the dry run (R16);
  a bad record discovered later → correct the overrides file and re-run (replace, R14), or roll back
  (R18).
