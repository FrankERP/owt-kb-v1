# Calendar picker, special services, local rule enforcement — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

> **Hardened across two review rounds**, six blockers, every one confirmed against source before acting.
>
> **Round 1** found that the one surface where the user's hard rule has to hold — the local filler on specials — did not exist in the codebase, was specified in a single sentence inside another task, and had an acceptance criterion a *rule-violating* filler satisfies. It is now Task 7. It also found P2's rename refusal keyed on a draft flag `handlePreview` resets, making it unreachable and the outcome a duplicate `special_role` in Sanity.
>
> **Round 2** found that Task 7 would have auto-seated five instruments and a FOH operator per special (`rowAppliesTo` is true for every non-`coro` row on every column type); that P7 asserted two contradictory fairness directions and Tasks 3 and 7 tested for both; that the unfilled-seat channel structurally cannot carry a special's date; and that with a preflight supplied `handleConfirm` never consults `d.exists` at all — so round 1's fix was still one race away from the duplicate document.

**Goal:** Three changes to the month generator, built together because they share one mechanism — a calendar replaces the date checkboxes, any weekday can become a named `special_role`, and the solver's hard rules (pairwise conflicts, person exclusions, week exclusions) are enforced locally in the grid's candidate ranking.

**Architecture:** Widen the column type end-to-end **first**, as a typed change with pinning tests around it, because five silent `===` branches and two silent pass-throughs decide weekend-vs-special today and all seven keep compiling when the type widens. Then the rules land as a new pure module. Then the calendar replaces the setup step's controls. The write path and the filler come last — the two parts that can put wrong data in Sanity or violate the rule the user asked for.

**Tech Stack:** Next.js 16, React 19, TypeScript, Tailwind, vitest (`environment: "node"`, per-file `@vitest-environment jsdom` for components). No solver changes — `gcf/owt_solver_v2.py` is untouched (E4, E10).

**Source spec:** [`docs/superpowers/specs/2026-07-30-calendar-specials-rules-design.md`](../specs/2026-07-30-calendar-specials-rules-design.md), approved at review round 5. **Facts and E-decisions are cited by number below and are not restated.** Where a task appears to contradict an E-decision, the decision governs and the task is wrong.

**Predecessor:** C · Planificador is merged to `main` — the feature landed at `cfd4c66`, fast-forwarded to `main` at `9eec3da`. `plannerModel`, `PlannerGrid`, `seatModel` and `candidateRanking` are all extended here, none replaced.

**The requirement in the user's own words**, because two of the decisions below only make sense against it:

> "I need some rules enforce**d** in specials. Specially that exclude two people from being together."
> "It has to be hard because if it's soft in fairness it will always choose people like Frank, Mkz or Gaby who tend to have 1 or 2 participations a month." · "yes, apply on the weekend grid"

### Task 9: Move the rules into Sanity (P6, closing O1)

**Files:** Create a schema under `sanity/schemas/`; create `app/api/admin/solver-config/route.ts`; modify `app/components/admin/MonthGenerator.tsx`, `app/components/admin/ServicesPanel.tsx`, `app/components/admin/SeatBoard.tsx`; create a guarded one-off under `scripts/`.

Last on purpose, and it depends on Task 3 rather than the reverse: `evaluate({ …, config })` takes the config as a parameter, so **where the rules are stored is orthogonal to whether they work**. Tasks 3–8 are complete and correct with the rules still in `localStorage`; this task is what makes the enforcement true for a *second admin* and on the *Tablero*.

**Steps**

**Ordering is load-bearing in this task.** The live rules are irreplaceable — they exist in exactly one browser — so the sequence below is not a suggestion: **0 → 4 → 1–3 → 5**. Getting it wrong destroys the artifact the task exists to preserve.

0. **Capture the `localStorage` JSON to a file before anything else in Task 9 ships.** Read `owt_solver_config_v3` out of the browser, save it in the repo working tree (untracked) or hand it over. Nothing else starts until this exists.
1. **Schema.** One singleton document holding `restrictions`, `conflicts`, `presence` and the pools — the shape already typed at `plannerModel.ts:109-152`. **Every array-of-object item needs a `_key`** (CLAUDE.md invariant); the rule objects already carry an `id` from `uid()` (`MonthGenerator.tsx:171`), so map `id` → `_key` rather than minting a second identifier. **The Studio deploy is for Studio visibility ONLY, and gates nothing here** — the Content Lake is schemaless, recorded twice in this repo (`docs/superpowers/plans/2026-06-24-multi-author-references.md:137`, `docs/DATA_MODEL.md:499-501`). *(An earlier draft claimed "the code cannot read a type the Content Lake does not have", which is false and misstated what gates what.)* Deploy it or not per step 7's decision, but do not sequence anything behind it.
2. **Read path — and it cannot be a server-side thread as first written.** The whole admin tree below `app/(client)/admin/page.tsx` is `"use client"` (`AdminPanel.tsx:1`, `ServicesPanel.tsx:1`), so either add a **GET** on the same route as step 3, or extend the prop chain and add `app/(client)/admin/page.tsx` and `app/components/admin/AdminPanel.tsx` to this task's file list. Say which. Then thread the config to **both** `MonthGenerator` and `SeatBoard`, which has no access at all today (fact 25) — `SeatBoard` calls `rankCandidates` with no config (`SeatBoard.tsx:112-113`), and passing one is what extends E6's hard blocks to the Tablero. **Thread the column type and date too** — `evaluate`'s `column` argument is optional (Task 3 step 2), and without it no pattern's service half can be matched, so a config alone gives the rules undefined scope. `SeatBoard` holds both in state, so this is one line. **State the known asymmetry:** week exclusions (E7) remain unevaluable on the Tablero, which has no Sunday spine (Task 3 step 2b) — conflicts and exclusions apply there, week rules do not.
2a. **Only the step-4 script may CREATE the document; the write route may only UPDATE.** Without this, the deployable state after steps 1–3 is: document absent → client shows `DEFAULT_SOLVER_CONFIG` → the first Guardar **creates the shared document from the defaults**, and step 4's script then either no-ops (`createIfNotExists` — the live rules are lost) or clobbers it (`createOrReplace`), or trips 2c's `_rev` check. That is blocker 2b's hazard entering by a different door. The route rejects a create with a stated reason; the script is the only thing that mints it.
2b. **Distinguish "document absent" from "read failed", or the fallback eats the rules.** Step 4 says outright that `DEFAULT_SOLVER_CONFIG` may no longer match what is in use, and step 5 makes that same constant the fallback while retiring the only other copy. The natural client shape — `const config = fetched ?? DEFAULT_SOLVER_CONFIG` inside a try/catch — turns a *transient fetch failure* into "the rules are the seeded defaults": one edit plus Guardar then replaces the shared document wholesale, and because these are now HARD blocks, enforcement silently degrades to whatever the defaults say in the meantime. **Absent document ⇒ fall back to defaults IN MEMORY ONLY — never written back. Failed or not-yet-loaded read ⇒ surface the error and REFUSE to save.** Two different states, never collapsed into one `??`, and neither one ever persists the defaults.
2c. **Carry `_rev` and reject a stale one.** Multi-admin is the entire point of P6, so last-write-wins is the wrong default. The codebase's own convention is a revision check with a `stale_revision` rejection — `ServiceRole._rev` is "sent with every mutation" (`serviceCardModel.ts:119-120`), enforced at `app/api/admin/roles/route.ts:258`. Follow it.
3. **Write path.** An admin-gated route (`requireActiveManager`). **No `revalidate*` call applies here** and adding one would be cargo cult: `app/utils/revalidate.ts` exports only `revalidateServiceViews`/`revalidateSongViews`, and this document is read solely inside a dynamic, session-gated admin tree with no ISR surface. Refresh client-side instead and say so in a comment, so the next reader does not "restore" a missing revalidation. The client handler wraps `fetch` in try/catch/finally, checks `res.ok`, resets its loading flag, and never closes-as-success on failure.
4. **Seed from step 0's file — this needs the user, runs BEFORE the read/write path is reachable in production, and the write must mint `_key`s.** Step 1 states the `_key` invariant for the schema; **the production write is where it actually has to happen**, and the `localStorage` JSON carries `id`, not `_key`. Map `id` → `_key` in the script, not just in the schema definition. **If the document already exists the script REFUSES and prints a diff** — it never overwrites, because at that point something else created it and that is the failure 2a exists to prevent. The live rules exist **only in one browser's `localStorage`**; `DEFAULT_SOLVER_CONFIG` (`MonthGenerator.tsx:118-167`) is just the first-run seed and may no longer match what is in use. Seeding from the constant would silently discard every edit made since. So: read `owt_solver_config_v3` out of the browser, hand it over as JSON, and seed from *that* — a `scripts/` one-off guarded by `--apply`, dry-run first, run with `node --env-file=.env.local`. **A production write needs explicit consent** (CLAUDE.md); diagnosing is not consent.
5. **Retire the `localStorage` read/write in the SAME change that lands the fetch** — they must not coexist. Both call `setSolverConfig`: the mount effect reads `owt_solver_config_v3` (`MonthGenerator.tsx:1026-1039`) and a second effect writes **every** `solverConfig` change straight back (`:1041-1043`), so with both live the fetched document is immediately mirrored into `localStorage` and the load order decides which wins — unspecified, and different on a cold load versus a re-render. Keep `DEFAULT_SOLVER_CONFIG` as the in-memory fallback (2b) so a fresh environment still works.
6. Update the Task 8 rule-panel copy — "rules live in this browser only" stops being true here.

7. Decide whether the rule document should be **hand-editable in Studio**. A new type in `sanity/schema.ts` is classified `editable` by `partitionStudioTypes` (`sanity/structure.ts:29-36`), which quietly creates a second write path around the admin-gated route — no `_rev` check, no validation.

**Verify:** the config survives a hard reload in a different browser profile; **a failed read refuses to save rather than offering the defaults** (step 2b — mutate the two states into one `??` and watch it fail); a stale `_rev` is rejected; **`SeatBoard` refuses a pair the planner grid refuses, as a pinned test** — this is a hard block newly appearing on a shipped surface, not a manual sanity check; an unauthenticated POST is rejected; the dry-run diff is reviewed before `--apply` runs.

**Done:** one source of rules for every admin and both surfaces — E6's "hard" is true beyond one browser.
